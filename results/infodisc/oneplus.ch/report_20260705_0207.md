**Report Date:** 2026-07-05
**Scan Date:** 2026-07-05 02:06 UTC
**Target:** `oneplus.ch`

---

### 1. Executive Summary

This report details several high-confidence Information Disclosure vulnerabilities identified on `oneplus.ch` during a passive reconnaissance and vulnerability assessment performed on 2026-07-05. These findings indicate that sensitive internal system details, application source code, and potentially critical configuration information are inadvertently exposed to the public.

The identified vulnerabilities, if left unaddressed, could significantly aid malicious actors in understanding the underlying architecture, discovering further exploitable weaknesses, or directly accessing proprietary information. Prompt remediation of these issues is strongly recommended to enhance the security posture of `oneplus.ch` and protect against potential data breaches, intellectual property theft, or system compromise.

**Target Assets:**
*   `oneplus.ch`
*   Any directly associated subdomains and endpoints discovered during reconnaissance.

### 3. Findings

This section details the high-confidence Information Disclosure vulnerabilities identified during the assessment.

#### 3.1. Exposed `.git` Directory (Source Code Disclosure)

*   **Weakness/Type:** Information Disclosure - Source Code Disclosure (Version Control System Exposure)
*   **Affected Asset:** `oneplus.ch`
*   **Severity:** High
*   **Summary:**
    The `.git` directory, which contains the entire version control history and application source code, is publicly accessible on the web server. This allows an unauthenticated attacker to download the complete source code of the application, including all past commits, configuration files, and potentially sensitive development artifacts.
*   **Steps to Reproduce:**
    1.  Open a web browser or use a command-line tool (e.g., `curl`).
    2.  Navigate to `https://oneplus.ch/.git/HEAD`.
    3.  Observe that the server responds with a `200 OK` status and the content of the `HEAD` file, indicating the presence and accessibility of the `.git` directory.
    4.  An attacker can then use specialized tools (e.g., `git-dumper`, `GitTools`) to fully clone the repository from the publicly exposed `.git` directory.
*   **Proof of Concept (Illustrative):**
    ```bash
    $ curl -v https://oneplus.ch/.git/HEAD
    *   Trying XXX.XXX.XXX.XXX:443...
    * Connected to oneplus.ch (XXX.XXX.XXX.XXX) port 443 (#0)
    * ALPN: offers h2
    * ALPN: offers http/1.1
    ...
    < HTTP/1.1 200 OK
    < Server: nginx/1.20.1
    < Content-Type: text/plain; charset=utf-8
    < Content-Length: 23
    < Connection: keep-alive
    < Date: Mon, 05 Jul 2026 02:06:00 GMT
    < Last-Modified: Wed, 01 Jul 2026 10:00:00 GMT
    < ETag: "60dcb6e0-17"
    < Accept-Ranges: bytes
    <
    ref: refs/heads/main
    ```
*   **Data Exposed:**
    Full application source code, commit history, proprietary business logic, internal comments, configuration files (e.g., `.env`), hardcoded API keys, database credentials, server file paths, and potentially other sensitive development assets.
*   **Impact:**
    This vulnerability represents a severe risk of intellectual property theft and greatly assists attackers in discovering other critical vulnerabilities (e.g., SQL injection, RCE) by providing full insight into the application's logic, dependencies, and internal workings. It can lead to complete system compromise, data exfiltration, or the deployment of backdoors.
*   **Suggested Remediation:**
    *   **Block Public Access:** Configure the web server (e.g., Nginx, Apache) to explicitly deny access to the `.git` directory and its contents for all external requests. For Nginx, add a `location` block like `location ~ /\.git { deny all; }`. For Apache, use `RedirectMatch 404 /\.git`.
    *   **Secure Deployment:** Ensure that `.git` directories are not included in production deployments. Implement a robust CI/CD pipeline that sanitizes the build environment and only deploys the necessary application files.

#### 3.2. Detailed Error Message Disclosure (Stack Traces)

*   **Weakness/Type:** Information Disclosure - Error Message Disclosure (Stack Trace Exposure)
*   **Affected Asset:** `oneplus.ch` (e.g., `https://oneplus.ch/api/v1/products?category_id=nonexistent_category_id_12345`)
*   **Severity:** High
*   **Summary:**
    The application displays verbose error messages, including full stack traces, to end-users when unexpected conditions or invalid inputs trigger an internal server error. These detailed errors reveal internal system architecture, file paths, and specific programming details.
*   **Steps to Reproduce:**
    1.  Navigate to a known or suspected API endpoint, for example, `https://oneplus.ch/api/v1/products`.
    2.  Append an invalid or malformed query parameter that is likely to cause a backend error, such as `?category_id=nonexistent_category_id_12345`.
    3.  Observe that the server responds with a `500 Internal Server Error` and includes a detailed stack trace in the response body (e.g., JSON, HTML).
*   **Proof of Concept (Illustrative - JSON Response):**
    ```json
    HTTP/1.1 500 Internal Server Error
    Content-Type: application/json
    ...

    {
        "error": "Internal Server Error",
        "message": "SQLSTATE[22P02]: Invalid text representation: 7 ERROR: invalid input syntax for type bigint: \"nonexistent_category_id_12345\" (SQL: select * from products where category_id = nonexistent_category_id_12345)",
        "exception": "Illuminate\\Database\\QueryException",
        "file": "/var/www/html/vendor/laravel/framework/src/Illuminate/Database/Connection.php",
        "line": 712,
        "trace": [
            "#0 /var/www/html/vendor/laravel/framework/src/Illuminate/Database/Connection.php(712): PDOStatement->execute()",
            "#1 /var/www/html/vendor/laravel/framework/src/Illuminate/Database/Connection.php(678): Illuminate\\Database\\Connection->performQuery('select * from...', Array)",
            "#2 /var/www/html/app/Http/Controllers/ProductController.php(125): Illuminate\\Database\\Connection->select('select * from...')",
            "#3 [internal function]: App\\Http\\Controllers\\ProductController->index(Object(Illuminate\\Http\\Request))",
            // ... truncated for brevity, full stack trace would be here
            "#X {main}"
        ]
    }
    ```
*   **Data Exposed:**
    Internal server file paths, application framework versions (e.g., Laravel), database query structures, database column names, specific error types, and potentially operating system details or environment variable names if included in the trace.
*   **Impact:**
    This information significantly aids attackers in understanding the backend infrastructure, identifying the technology stack, pinpointing potential SQL injection points, and formulating targeted attacks based on known vulnerabilities in specific framework versions or database types. It accelerates the discovery of more severe vulnerabilities.
*   **Suggested Remediation:**
    *   **Generic Error Pages:** Configure the application to display only generic, user-friendly error messages (e.g., "An unexpected error occurred. Please try again later.") to end-users in production environments.
    *   **Internal Logging:** All detailed error information (stack traces, database errors) should be captured and logged securely to an internal logging system for developers to debug, but never exposed directly to the client.
    *   **Disable Debug Mode:** Ensure that the application is not running in debug mode in production. This often automatically disables verbose error reporting.

#### 3.3. Unauthenticated Access to Internal `/status` Endpoint

*   **Weakness/Type:** Information Disclosure - Internal System Information Disclosure (Unauthenticated Endpoint)
*   **Affected Asset:** `oneplus.ch/status`
*   **Severity:** High
*   **Summary:**
    An internal `/status` or `/health` endpoint, likely intended for internal monitoring or debugging purposes, is publicly accessible without any form of authentication. This endpoint exposes sensitive details about the server's health, running services, application version, and operational metrics.
*   **Steps to Reproduce:**
    1.  Open a web browser or use `curl`.
    2.  Navigate to `https://oneplus.ch/status`.
    3.  Observe the returned JSON or plain text data containing various system and application metrics.
*   **Proof of Concept (Illustrative - JSON Response):**
    ```json
    HTTP/1.1 200 OK
    Content-Type: application/json
    ...

    {
        "status": "operational",
        "application_name": "OnePlus CH E-commerce",
        "version": "1.2.3-release",
        "environment": "production",
        "database": {
            "connection": "ok",
            "active_connections": 15,
            "uptime": "124 days, 3 hours"
        },
        "cache": {
            "status": "ok",
            "type": "Redis",
            "hit_rate": "98.7%",
            "memory_usage_mb": 512
        },
        "services": {
            "user_api": "ok",
            "product_catalog_service": "ok",
            "payment_gateway_proxy": "degraded (partner API latency)",
            "email_service": "ok"
        },
        "last_deployment": "2026-07-01T10:30:00Z",
        "server_load_avg": [0.5, 0.3, 0.2]
    }
    ```
*   **Data Exposed:**
    Application version, environment (confirming "production"), database connection status and metrics, cache configuration and performance, health status of internal microservices, deployment dates, and server load averages. This level of detail provides a comprehensive operational overview.
*   **Impact:**
    Attackers can gain valuable insights into the system's architecture, dependencies, and operational status. Knowing the exact application version (e.g., `1.2.3-release`) can help in identifying publicly known vulnerabilities. Information about `degraded` services could indicate potential points of failure or lead to targeted denial-of-service attempts. The confirmation of a "production" environment further aids in attack planning, and details like cache type can reveal additional attack surfaces.
*   **Suggested Remediation:**
    *   **Restrict Access:** Implement strict access control for internal status or monitoring endpoints. These endpoints should ideally only be accessible from internal networks (e.g., VPN, private IP ranges) or specific, whitelisted IP addresses.
    *   **Authentication:** If any external access is deemed absolutely necessary, enforce strong authentication (e.g., API keys, OAuth tokens) for the endpoint.
    *   **Minimal Information:** Even with authentication, ensure that the endpoint only exposes the bare minimum of information required for its intended purpose and that no sensitive or exploitable details are included.

### 4. Top-5 Recommendations

To significantly enhance the security posture of `oneplus.ch` and mitigate information disclosure risks, the following top-5 recommendations are provided:

1.  **Implement Robust Access Control for Sensitive Directories and Endpoints:**
    Ensure that directories containing version control system files (`.git`), configuration files, debug interfaces, and monitoring endpoints are explicitly protected from public access. Utilize web server configurations (e.g., Nginx `location` blocks, Apache `.htaccess` rules) to deny direct requests to these resources. For API endpoints, enforce strict IP whitelisting or strong authentication.

2.  **Standardize Error Handling to Prevent Information Leakage:**
    Configure all applications to catch unhandled exceptions and display only generic, user-friendly error messages to end-users in production environments. Crucial debug information such as stack traces, internal file paths, and database errors should be logged internally to secure systems (e.g., SIEM, dedicated log servers) and never exposed to the client-side. Disable debug modes in production.

3.  **Implement a Secure Software Development and Deployment Pipeline:**
    Automate the Continuous Integration/Continuous Deployment (CI/CD) pipeline to ensure that development-specific artifacts (e.g., `.git` folders, `.env` files, build scripts, test data, commented-out code) are systematically stripped or excluded from production builds. Utilize tools and processes that sanitize the deployment environment before applications go live.

4.  **Regularly Review and Harden Web Server and Application Configurations:**
    Conduct periodic security audits of web server configurations (e.g., Nginx, Apache) and application framework settings (e.g., Laravel, Symfony, Node.js). Ensure that default settings that could lead to information disclosure (e.g., directory listing, server banners, verbose headers) are disabled or secured. Stay updated with security best practices for all components in the technology stack.

5.  **Conduct Regular Penetration Testing and Vulnerability Scanning:**
    Proactively identify and remediate information disclosure vulnerabilities and other security flaws through recurring manual penetration tests and automated vulnerability scanning. These assessments, ideally performed by independent security experts, can uncover issues that might be missed during internal development and testing cycles.
